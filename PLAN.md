# Рацион на двоих

## Формат

Мобильное веб-приложение с установкой на главный экран (PWA). Одна ссылка для обоих телефонов, один общий аккаунт Supabase с почтой и паролем. GitHub хранит исходники, GitHub Pages публикует интерфейс, Supabase хранит личные данные. Собственный сервер не нужен.

## Пользовательский сценарий

1. Войти на обоих телефонах в один аккаунт.
2. Указать бюджет недели, приёмы пищи, время готовки, исключённые продукты и оборудование.
3. Уточнить цены упаковок и продукты, которые уже есть дома.
4. Собрать меню на неделю, при необходимости заменить блюда.
5. Получить общий список покупок, отмечать купленное в магазине.

## Этап 1 — рабочая основа (реализован)

- Адаптивные экраны: неделя, покупки, рецепты, настройки.
- 15 готовых рецептов, 21 продукт. Ингредиенты на порцию, общее меню на 2 порции.
- Подбор 250 вариантов меню с проверкой ограничений и бюджета. Если подходящий по цене вариант не найден, показываем превышение. Это поиск вариантов, а не доказательство минимальной стоимости.
- Два показателя стоимости: использованные ингредиенты и реальная закупка целых упаковок за вычетом домашних запасов.
- Локальный деморежим и облачный адаптер Supabase Auth + Postgres.
- Синхронизация раз в 10 секунд при открытом приложении. Контроль версии для защиты от потери одновременных изменений.
- Манифест, иконки, кеш интерфейса PWA. Офлайн-редактирование облачных данных пока не реализовано.
- Автоматическая публикация через GitHub Actions, тесты расчётов.

## Этап 2 — подключение и использование

- Опубликовать проект в D3SKII/diet, включить GitHub Pages.
- Создать Supabase-проект, выполнить SQL, создать один аккаунт, вставить публичные параметры подключения.
- Проверить вход и синхронизацию на двух телефонах, затем добавить на главный экран.
- Заменить демонстрационные цены и протестировать меню на реальной неделе.

## Этап 3 — полезные улучшения

1. Свои рецепты и продукты, избранные блюда.
2. Готовка на 2–3 дня: одна большая порция на несколько приёмов пищи.
3. История недель и фактические расходы: планировали / потратили.
4. Перенос остатков упаковок на следующую неделю, подтверждение пополнения запасов.
5. Разные порции для каждого и дополнительные личные приёмы пищи.
6. Восстановление из резервной копии, архив меню.
7. КБЖУ — после добавления проверенной базы состава продуктов. Сейчас цифры не выдумываем.

Автоматические цены магазинов и генерацию рецептов ИИ откладываем: для личного инструмента ручные цены проще поддерживать и проверять.

## Структура

```text
public/
  index.html          оболочка
  app.js              экраны и действия
  style.css           мобильная адаптация
  data.js             рецепты и продукты
  domain.js           расчёты и подбор меню
  storage.js          локальное/облачное хранение и вход
  config.js           публичные настройки Supabase
  manifest.webmanifest
  sw.js               кеш интерфейса
supabase/schema.sql   таблица, правила доступа, запись с контролем версии
scripts/serve.mjs     локальный просмотр
scripts/build.mjs     сборка статических файлов
tests/                тесты расчётов
.github/workflows/    автоматическая публикация
```

## Модель данных

Одна строка `household_state` на общий аккаунт: `owner_id`, `revision`, `payload`, `updated_at`. В `payload`: настройки, цены, запасы, меню 7 × 3, отмеченные покупки. Каждая новая запись проверяет предыдущую версию. Чужие аккаунты не видят строку благодаря RLS. Для текущего объёма это проще отдельных таблиц; при добавлении истории и своих рецептов данные можно разделить.

## Границы первой версии

Одна текущая неделя без календарных дат; одинаковые блюда и порции для обоих. Цены примерные, без связи с магазинами. Соль/специи не считаются. Исключения работают по ингредиентам из каталога, а не по полноценной базе аллергенов. Облачный путь необходимо проверить после настройки Supabase. Размещение зависит от условий GitHub Pages и Supabase; бесплатный тариф не означает гарантию непрерывной доступности.
